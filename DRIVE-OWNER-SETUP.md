# MUSES R18: personal Drive authorization

The app uses Google OAuth read-only Drive access. No token, client secret, account email, or personal folder ID is committed. A first successful connection checks the actual Drive user's permissionId and asks to bind this device profile to that owner; other accounts are rejected. The pin and folder ID live only on that browser/device. A public code repository is not an authentication boundary. Do not publish personal archives.

- Web: enable Drive API in a Google Cloud project, configure the OAuth consent screen (personal account as test user if appropriate), register a Web OAuth client and the exact HTTPS origin, then enter the client ID in MUSES > Settings > Google Drive. Browser access tokens are memory-only and expire; a user action may be necessary to reauthorize.
- Android: enable Drive API; register an Android OAuth client with the exact installed APK package and SHA-1 signing certificate fingerprint. The native authorization bridge uses Google Play services rather than an embedded login page. The existing signed private APK workflow must run; it is skipped for a public repository.
- P90X: the app uses an owned folder selected in Settings, or finds a unique owned folder named p90x classic. It maps complete video files by DVD number. Missing local videos are downloaded with the approved owner's token, validated and stored in the existing local media archive. Offline cached copies remain on that device; disconnect stops Drive requests but does not delete personal videos or study records.
- For continuous cross-device sessions or background refresh, use a separately secured server with authorization-code flow and encrypted refresh tokens, and an owner allowlist. This repo has no such deployed backend. Local device profile binding is not an app-level lock or a replacement for OS login.
- Real Google sign-in, account mismatch rejection with live accounts, and Android playback must be tested on the configured and signed application before calling this production-ready.
